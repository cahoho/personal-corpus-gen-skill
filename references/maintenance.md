# 内容维护、迭代与质量检查

## 更新、冲突与时间

1. 从用户提供或已授权的输入及任务相关笔记开始，先判断是新事实、补充、更正、过时、不同场景还是同义重复；非必要不读取私密区。
2. 对用户明确纠正，保留更正的依据及时间；旧值有理解历史变化的价值时，用简短的“此前/现今”并列记录。没有历史价值时可更新当前事实，但不要擅自丢掉重要来源或把变更时间当作事实生效时间。
3. 对来源相互矛盾、时间不明或无法判断场景的内容，分别记录并标注不确定；非敏感内容可放 Inbox 待确认。关键隐私不在普通 Inbox 留事实或可反推的标题。
4. 依据、来源和适用时间不同的条目分别标注；避免一个文件级属性错误覆盖整篇。更新 `last_mentioned` 只能依据已处理且时间可靠的对应用户表达。
5. 用户手改与自动提案冲突时暂停并展示差异；不要覆盖。合并/拆分笔记后维护必要的 wikilink、主 MOC 与来源，不能让同一事实在多个副本出现不一致。

## 写入前后

- 首次导入先预览小样本并取得全量许可；普通增量在明确授权范围内按批汇报，不必逐条打断。
- 批量迁移、覆盖、删除或改变既有含义：列出路径、变更与风险，确认后执行。若目标位于个人目录，还应遵守运行环境有关扫描、备份、删除和确认的安全规则。
- 修改已有内容前准备适当的可恢复方案；备份可能包含隐私，说明存放与保留风险。写前比对文件当前状态，避免覆盖用户同时编辑的内容；失败或冲突时停止并报告，标明已成功与未完成的部分。
- 仅在实际写入并验证后更新导入完成标记。中断恢复时检查目标文件、来源定位与批次状态；不因为中间报告存在就假设写入已成功。导入进度记录只保存必要标识和状态，不存聊天正文。
- 删除用户指定记忆时先列已知正式内容、待确认项、来源摘录、MOC、导出和备份中的相关副本，区分可操作范围与不可控副本；取得确认并遵守环境安全规则。不能保证删除其他平台、外部模型缓存或未知备份。

## Schema 和模板演化

- Vault 内 `SCHEMA.md` 是该库当前约定；Skill 更新不能静默覆盖。修改规范前先比较版本、用户定制、模板与已有字段，说明变更与兼容策略。
- 批量迁移须预览、确认、备份、执行并验证；保留旧链接或提供可核对的重定向方案。禁止因模板升级重建和覆盖已有人格画像。
- 不为每次导入增加字段。只有能够改善可追溯性或检索的规则才纳入 Schema，降低维护成本。

## 验收清单

- 重复导入：同一会话/消息不重复成文，不覆盖人工修改；不同来源同一事实合并且均可追踪。
- 语义：用户自述、第三方叙述、AI 生成和推断相互区分；未知、冲突及过时不伪装为确定事实。
- 时间：事件时间、消息时间、文档修改时间不混淆；近期范围之外、未导入数据及未选分支被明确列为未覆盖。
- 隐私：普通检索能实际排除 `07 Privacy/`；常规 MOC、来源、清单、日志与导出无敏感正文或标题泄漏。
- Obsidian：frontmatter 有效，相关 wikilink 指向存在的笔记；不依赖插件、无大量无用节点或重复事实。
- 导入报告：成功、失败、跳过、待确认和覆盖范围可核对；不把助手运行完成当成所有源数据已处理。
